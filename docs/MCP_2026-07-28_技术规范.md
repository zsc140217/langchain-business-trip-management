## 1. 协议概述

### 1.1 定义

**Model Context Protocol (MCP)** 是一个开放的标准化协议，用于AI模型与外部工具、资源和服务之间的通信。

### 1.2 核心特性

- **协议无关传输**：支持stdio、HTTP、SSE等多种传输方式
- **基于JSON-RPC**：所有消息使用JSON-RPC 2.0格式
- **无状态设计**（2026-07-28）：每个请求自包含，无需协议级会话
- **能力协商**：客户端和服务器动态声明支持的功能
- **可扩展性**：通过扩展机制支持自定义功能

### 1.3 协议演进

| 版本 | 发布日期 | 主要特性 |
|------|---------|---------|
| 2024-11-05 | 2024年11月 | 初始版本，有状态握手，HTTP+SSE |
| 2025-03-26 | 2025年3月 | 引入Streamable HTTP |
| 2025-11-25 | 2025年11月 | 最后一个有状态版本 |
| **2026-07-28** | **2026年7月** | **无状态重构，移除initialize握手** |

## 2. 架构设计

### 2.1 三层架构

```
┌──────────────────────────────────────────────┐
│              Host Application                │
│         (Claude Desktop, VS Code)            │
│                                              │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  │
│  │ Client 1 │  │ Client 2 │  │ Client N │  │
│  └─────┬────┘  └─────┬────┘  └─────┬────┘  │
└────────┼─────────────┼─────────────┼────────┘
         │             │             │
         ▼             ▼             ▼
    ┌────────┐    ┌────────┐    ┌────────┐
    │Server 1│    │Server 2│    │Server N│
    │(Files) │    │  (DB)  │    │ (API)  │
    └────────┘    └────────┘    └────────┘
```

### 2.2 Host（宿主）

**职责：**
- 运行AI模型（LLM）
- 创建和管理多个Client实例
- 执行安全策略和用户授权
- 协调AI采样和上下文聚合
- 处理用户交互和UI展示

### 2.3 Client（客户端）

**职责：**
- **1:1关系**：每个Client连接恰好一个Server
- 在每个请求上附加协议版本和能力声明
- 双向路由协议消息
- 管理订阅和通知
- 维护Server间的安全边界

### 2.4 Server（服务器）

**职责：**
- 通过MCP原语暴露功能：
  - **Tools**：可调用的函数/操作
  - **Resources**：可读取的数据源
  - **Prompts**：提示词模板
- 独立运行，职责单一
- 通过`InputRequiredResult`请求客户端输入
- 遵守安全约束
- 可以是本地进程或远程服务

### 2.5 设计原则

1. **Server极易构建**：Host处理复杂编排，Server专注特定功能
2. **Server高度可组合**：独立提供功能，可无缝组合
3. **Server隔离性**：不能读取完整对话，不能互相"看到"
4. **渐进式功能增强**：核心协议最小化，额外能力按需协商

## 3. 传输层协议

MCP是**传输无关**的协议，协议语义在所有传输方式上相同。

### 3.1 标准传输：stdio

**适用场景：** 本地子进程通信

**消息格式：**
- 每条消息一行，UTF-8编码
- 以换行符(`\n`)分隔
- 消息**不能**包含嵌入的换行符

**流：**
- `stdin`：Client → Server（请求、通知）
- `stdout`：Server → Client（响应、通知）
- `stderr`：Server日志（可选，Client可忽略）

**取消：** Client发送`notifications/cancelled`通知

**关闭：**
1. Client关闭stdin
2. Server检测EOF并退出
3. 超时后Client强制终止进程

### 3.2 标准传输：Streamable HTTP

**适用场景：** 远程Server、负载均衡、HTTP缓存

**核心机制：**
- 每个JSON-RPC消息是独立的HTTP POST
- Server可返回单个JSON或SSE流
- 必需HTTP头：`MCP-Protocol-Version`, `Mcp-Method`, `Mcp-Name`

**请求示例：**
```http
POST /mcp HTTP/1.1
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: get_weather
Content-Type: application/json

{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{...}}
```

**取消：** Client关闭SSE响应流

## 4. 消息格式与模式

### 4.1 JSON-RPC 2.0

所有MCP消息使用JSON-RPC 2.0，UTF-8编码。

### 4.2 请求元数据（_meta）

**每个请求必须携带：**
```json
{
  "params": {
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientInfo": {
        "name": "my-client",
        "version": "1.0.0"
      },
      "io.modelcontextprotocol/clientCapabilities": {}
    }
  }
}
```

### 4.3 消息流向约束

- Client → Server：请求、通知
- Server → Client：响应、通知
- **Server不能发起JSON-RPC请求**
- **Client不能发送JSON-RPC响应**

## 5. 协议生命周期（2026-07-28）

### 5.1 无状态模型

**关键变化：移除`initialize`/`initialized`握手。**

**旧版（2025-11-25及之前）：**
```
Client → initialize
Server → initialized + Session ID
Client后续请求带Session ID
```

**新版（2026-07-28）：**
```
Client → 任何请求（带_meta）
Server → 响应（无Session）
```

### 5.2 可选的服务发现

Client可以在第一次请求前调用`server/discover`：

```json
// 请求
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "server/discover",
  "params": {"_meta": {...}}
}

// 响应
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "protocolVersion": "2026-07-28",
    "serverInfo": {"name": "my-server", "version": "1.0"},
    "capabilities": {
      "tools": {"listChanged": true}
    }
  }
}
```

**注意：** `server/discover`是可选的，Client可以直接发送其他请求。

## 6. 能力协商机制

### 6.1 能力声明

**Client能力（在_meta.io.modelcontextprotocol/clientCapabilities中声明）：**
- `sampling`：支持AI采样请求
- `elicitation`：支持用户输入引导
- `roots`：支持根路径管理

**Server能力（在server/discover响应或能力字段中声明）：**
- `tools`：提供工具调用
  - `listChanged`：工具列表变化时发送通知
- `resources`：提供资源访问
  - `subscribe`：支持资源订阅
  - `listChanged`：资源列表变化时发送通知
- `prompts`：提供提示词模板
  - `listChanged`：提示词列表变化时发送通知

### 6.2 能力协商流程

```
Client发送请求（带clientCapabilities）
     ↓
Server检查clientCapabilities
     ↓
Server根据自身capabilities处理
     ↓
Server返回响应（可能包含InputRequiredResult）
```

**示例：**
```json
{
  "params": {
    "_meta": {
      "io.modelcontextprotocol/clientCapabilities": {
        "sampling": {},
        "elicitation": {}
      }
    }
  }
}
```

Server看到Client支持`elicitation`，可以在响应中返回`InputRequiredResult`要求用户输入。

### 6.3 能力约束

- 双方必须尊重声明的能力
- Server不能使用Client未声明的能力
- Client不能期望Server提供未声明的能力

## 7. 服务端特性

### 7.1 工具（Tools）

**定义：** AI模型可以调用的函数或操作。

**工具发现：**
```json
// 请求
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/list",
  "params": {"_meta": {...}}
}

// 响应
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "resultType": "complete",
    "tools": [
      {
        "name": "get_weather",
        "description": "Get weather for a location",
        "inputSchema": {
          "type": "object",
          "properties": {
            "location": {"type": "string"}
          },
          "required": ["location"]
        }
      }
    ],
    "ttlMs": 300000,
    "cacheScope": "public"
  }
}
```

**工具调用：**
```json
// 请求
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "get_weather",
    "arguments": {
      "location": "Beijing"
    },
    "_meta": {...}
  }
}

// 响应
{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "resultType": "complete",
    "content": [
      {"type": "text", "text": "Beijing: 22°C, Sunny"}
    ],
    "isError": false
  }
}
```

**工具名称规范：**
- 长度：1-128字符
- 允许字符：A-Z, a-z, 0-9, _, -, .
- 区分大小写
- Server内唯一

### 7.2 资源（Resources）

**定义：** AI可以读取的数据源。

**资源列表：**
```json
{
  "method": "resources/list",
  "params": {"_meta": {...}}
}
```

**资源读取：**
```json
{
  "method": "resources/read",
  "params": {
    "uri": "file:///project/README.md",
    "_meta": {...}
  }
}
```

**常见URI Scheme：**
- `file://`：本地文件
- `http://` / `https://`：远程资源
- `database://`：数据库记录
- 自定义scheme

### 7.3 提示词（Prompts）

**定义：** 预定义的提示词模板。

```json
{
  "method": "prompts/list",
  "params": {"_meta": {...}}
}
```

### 7.4 缓存提示

**2026-07-28新增：list响应携带缓存提示。**

```json
{
  "result": {
    "tools": [...],
    "ttlMs": 300000,        // 缓存5分钟
    "cacheScope": "public"  // 所有用户共享
  }
}
```

**cacheScope值：**
- `public`：所有用户可共享（如API文档）
- `user`：同一用户可共享（如用户特定数据）
- `private`：不可共享（如临时数据）

## 8. 2026-07-28架构重构

### 8.1 核心变化总结

| 特性 | 旧版（2025-11-25） | 新版（2026-07-28） |
|------|-------------------|-------------------|
| 握手 | 需要initialize/initialized | 无握手 |
| Session | 协议级Session ID | 无Session |
| 请求元数据 | 握手时交换一次 | 每个请求携带_meta |
| 服务发现 | initialize响应 | 可选的server/discover |
| Server发起请求 | 可以（sampling、elicitation等） | 不能（改用MRTR） |
| 负载均衡 | 需要粘性会话 | 普通轮询 |
| 缓存 | 不支持 | 支持ttlMs和cacheScope |
| GET流端点 | 有 | 移除 |

### 8.2 多轮往返请求（MRTR - Multi Round-Trip Requests）

**问题：** 无状态下如何实现Server请求Client输入？

**旧版方案：**
```
Client → Server: 调用工具
       ← Server发起请求: sampling/createMessage
Client → Server: 响应采样
       ← Server: 工具结果
```
问题：需要Server能发起JSON-RPC请求。

**新版方案（MRTR）：**
```
Client → Server: tools/call (第1次)
       ← Server: InputRequiredResult + requestState

Client → Server: tools/call (第2次，带inputResponses)
       ← Server: 最终结果
```

**InputRequiredResult格式：**
```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "resultType": "input_required",
    "inputRequests": {
      "confirm": {
        "method": "elicitation/create",
        "params": {
          "mode": "confirm",
          "message": "确认执行此操作？"
        }
      }
    },
    "requestState": "eyJvcGVyYXRpb24iOiJ0cmFuc2ZlciJ9"
  }
}
```

**重试请求：**
```json
{
  "jsonrpc": "2.0",
  "id": 3,  // 注意：ID必须不同
  "method": "tools/call",
  "params": {
    "name": "transfer",
    "arguments": {...},
    "inputResponses": {
      "confirm": {
        "action": "accept"
      }
    },
    "requestState": "eyJvcGVyYXRpb24iOiJ0cmFuc2ZlciJ9",
    "_meta": {...}
  }
}
```

**关键点：**
- `requestState`：Server返回的不透明字符串，Client原样传回
- JSON-RPC `id`：第2次请求必须使用不同的ID
- Client负责收集用户输入并重新发起请求

### 8.3 订阅与通知

**长期通知通过subscriptions/listen获取：**

```json
// 请求
{
  "method": "subscriptions/listen",
  "params": {
    "toolsListChanged": true,
    "resourceSubscriptions": [
      {"uri": "file:///project/config.json"}
    ],
    "_meta": {...}
  }
}

// 响应：SSE流
data: {"jsonrpc":"2.0","method":"notifications/tools/list_changed"}

data: {"jsonrpc":"2.0","method":"notifications/resources/updated","params":{...}}
```

**通知类型：**
- `notifications/tools/list_changed`：工具列表变化
- `notifications/resources/list_changed`：资源列表变化
- `notifications/resources/updated`：资源内容更新
- `notifications/prompts/list_changed`：提示词列表变化

**请求相关通知（不通过subscriptions/listen）：**
- `notifications/progress`：进度更新
- `notifications/message`：日志消息

这些通知只在请求的响应流中发送。

### 8.4 显式状态 vs 隐式状态

**旧版（隐式状态）：**
```
Session中存储：
- 用户身份
- 上下文信息
- 临时数据

问题：AI模型看不到这些状态
```

**新版（显式状态）：**
```json
// 第1次调用返回handle
{
  "result": {
    "upload_id": "upload_123",
    "message": "已上传第1块"
  }
}

// 第2次调用传递handle
{
  "params": {
    "name": "continue_upload",
    "arguments": {
      "upload_id": "upload_123",  // 显式传递
      "chunk": 2
    }
  }
}
```

**优点：**
- AI能看到状态（upload_id）
- AI能推理状态的含义
- 日志中直接可见状态
- 可以同时管理多个状态

## 9. 向后兼容性

### 9.1 检测旧版Server

**stdio传输：**

Client发送`server/discover`探测：
- 返回`DiscoverResult`：现代Server
- 返回`UnsupportedProtocolVersionError`：现代Server但版本不匹配
- 返回其他错误或超时：旧版Server，回退到`initialize`握手

**Streamable HTTP传输：**

Client POST到MCP端点：
- 返回200/400且有JSON-RPC响应：现代Server
- 返回404且无JSON-RPC响应：可能是旧版HTTP+SSE端点

### 9.2 版本协商

**Client支持的版本列表：**
```json
{
  "params": {
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28"
    }
  }
}
```

**Server不支持时返回：**
```json
{
  "error": {
    "code": -32100,
    "message": "Unsupported protocol version",
    "data": {
      "supported": ["2025-11-25", "2025-03-26"]
    }
  }
}
```

Client应选择双方都支持的最新版本。

## 10. 实现指南

### 10.1 Server实现清单

**必需：**
- [ ] 选择传输方式（stdio或Streamable HTTP）
- [ ] 实现JSON-RPC消息处理
- [ ] 解析和验证`_meta`字段
- [ ] 实现至少一个特性（tools、resources或prompts）
- [ ] 声明capabilities
- [ ] 处理协议版本协商

**推荐：**
- [ ] 实现`server/discover`
- [ ] 支持缓存提示（ttlMs, cacheScope）
- [ ] 确定性排序工具列表
- [ ] 实现取消处理
- [ ] 提供详细的错误信息

**可选：**
- [ ] 实现MRTR（如需用户确认）
- [ ] 支持订阅通知
- [ ] 实现自定义扩展

### 10.2 Client实现清单

**必需：**
- [ ] 选择传输方式
- [ ] 在每个请求中包含`_meta`
- [ ] 处理JSON-RPC响应和错误
- [ ] 实现协议版本协商
- [ ] 处理Server返回的capabilities

**推荐：**
- [ ] 实现`server/discover`探测
- [ ] 缓存工具列表（遵守ttlMs）
- [ ] 实现取消机制
- [ ] 处理向后兼容性

**可选：**
- [ ] 实现MRTR处理
- [ ] 支持订阅通知
- [ ] 实现自定义扩展

### 10.3 安全注意事项

**Server端：**
- 验证所有输入
- 实施认证和授权
- 限制资源访问范围
- 避免在工具参数中暴露敏感信息（不要用x-mcp-header标记密钥）
- 验证`Origin`头（Streamable HTTP）
- 只绑定localhost（本地Server）

**Client端：**
- 验证Server证书（HTTPS）
- 实施用户确认机制
- 清晰显示正在调用的工具
- 限制工具调用权限
- 记录审计日志

### 10.4 性能优化

**Client端：**
- 缓存工具列表（遵守ttlMs）
- 并行发送独立请求
- 复用HTTP连接

**Server端：**
- 确定性排序工具列表（提高LLM缓存命中）
- 实现增量更新通知
- 使用流式响应处理大数据
- 及时响应取消请求
