### Q5: LangChain 和 Spring AI 在工具调用上有什么区别？

**用户回答**：
> "这我只知道spring ai的工具调用是维护一个toolcallback类集中管理"

**评分**：⚠️ 50分（需加强）

- ⚠️ 只记得部分（Spring AI 的管理方式）
- ❌ 缺少定义方式、执行机制的对比

**需要记住的核心区别**：
| 维度 | Spring AI | LangChain |
|------|-----------|-----------|
| **定义工具** | `@Bean` + `@Description` | `@tool` 装饰器 |
| **管理方式** | `FunctionCallbackContext` 集中管理 | 工具列表传给 Agent |
| **执行机制** | Advisor（洋葱模式） | Chain（管道模式） |
| **特点** | 企业级（类型安全、依赖注入） | 灵活（快速开发、生态丰富） |

**标准回答**：
> "主要区别：
> - **定义**：Spring AI 用 `@Bean` + `@Description`，返回 `Function<Request, Response>`；LangChain 用 `@tool` 装饰器直接在函数上定义。
> - **管理**：Spring AI 通过 `FunctionCallbackContext` 集中注册管理；LangChain 工具是独立对象，通过列表传给 Agent。
> - **执行**：Spring AI 是 Advisor（洋葱模式）层层包装；LangChain 是 Chain（管道模式）流式处理。
> - **本质**：Spring AI 更企业级（类型安全），LangChain 更灵活（快速开发）。"

### Q2: RRF 融合是什么？为什么不直接用加权平均？

**用户回答**：
> "rrf是倒序索引融合，通过调节k值，可以改变高排名的影响，一般k越高，高排名（1名）的影响就越小"

**评分**：⚠️ 65分（及格，需补充）

**优点**：
- ✅ 理解 RRF 的核心机制（排名融合）
- ✅ 知道 k 值的作用
- ✅ 理解 k 值对高排名的影响

**问题点**：
- ⚠️ 术语：应该是 "**Reciprocal Rank Fusion（倒数排名融合）**"
- ❌ **没回答第二问**：为什么不直接用加权平均？
- ⚠️ 没说明具体计算公式

**标准回答**：
> "RRF（Reciprocal Rank Fusion，倒数排名融合）的公式是 `score = Σ [1/(k+rank)]`，k 一般取 60。
> 
> **为什么不用加权平均？** 因为三路召回的分数不在同一量级：
> - BM25 分数可能是 0-10
> - Dense 余弦相似度是 0-1
> - 直接加权需要先归一化，引入更多超参数
> 
> **RRF 的优势**：只看排名不看分数，天然归一化。k 值越大，对高排名的偏好越弱，让排名更平滑。"

### Q5: 项目的召回率和准确率分别是多少？如何评估的？

**用户回答**：
> "召回率靠真阳性除以真阳性加假阴性，准确率靠真阳性除以真阳性加真阴性。我记得真是实际的，阳是模型判断的"

**评分**：⚠️ 40分（需加强）

**问题点**：
- ✅ 召回率公式正确：Recall = TP / (TP + FN)
- ❌ **准确率公式错误**：应该是 **Precision = TP / (TP + FP)**
- ❌ **混淆了 Precision（精确率）和 Accuracy（准确率）**
- ❌ 对"真/假"和"阳/阴"的理解有误
- ❌ **没回答项目的具体数值和评估方法**

**正确理解混淆矩阵**：
```
          实际正类    实际负类
预测正类    TP        FP
预测负类    FN        TN
```

- **TP（真阳性）**：预测正✓，实际正✓
- **FP（假阳性）**：预测正✓，实际负✗
- **FN（假阴性）**：预测负✗，实际正✗
- **TN（真阴性）**：预测负✓，实际负✓

**核心指标**：
- **Recall（召回率）** = TP / (TP + FN) — 实际正类中，找回了多少
- **Precision（精确率）** = TP / (TP + FP) — 预测为正类的，有多少是对的

**标准回答**：
> "项目评估指标：
> - **召回率 85%**：100 个相关文档，召回了 85 个
> - **精确率 90%**：返回 10 个文档，9 个是相关的
> 
> 评估方法：
> 1. 构建测试集：50 个真实用户问题 + 人工标注的相关文档
> 2. 对比检索结果和标注答案
> 3. 计算 Recall、Precision、F1-Score
> 
> 优化后效果：召回率从 60% → 85%，精确率从 75% → 90%。"

   - 共 3 个查询分别检索，最后融合

4. **RRF 为什么不用加权平均**
   - 三路分数不在同一量级（BM25: 0-10，Dense: 0-1）
   - 加权平均需要归一化，引入更多超参数
   - RRF 只看排名，天然归一化

### 🟡 中优先级（需要熟悉）

5. **BM25 vs Dense 的优缺点和场景**
   - BM25：精确但不理解语义，适合专有名词、否定词
   - Dense：理解语义但对精确关键词不敏感，适合同义词、意图理解

6. **生产环境数据库选型**
   - BM25：Elasticsearch / OpenSearch
   - 向量：Milvus / Qdrant / Weaviate / Postgres + pgvector

7. **排查思路要分场景**
   - 召回低 → 放宽阈值、提高 Top-K
   - 精确低 → 检查各路召回、否定词处理

>

> 2. 有 Model-based 时：final_score = 0.6 × code_score + 0.4 × model_score
> 3. 只有 Code-based 时：final_score = code_score
> 
> **一票否决**：
> - 如果 Code-based 检测到 CRITICAL 问题（预算超标），不管 Model-based 分数多高，最终级别都是 CRITICAL，直接阻断发布
>

> - ≥ 0.50 → MEDIUM（中等问题）
> - < 0.50 → HIGH（严重问题）
> 
> 这样设计保证了政策合规零容忍，从技术层面强制执行企业政策。"

**详细文档**：见 `tests/evaluation/comprehensive_eval_framework.py` 和 `面试复习-含Eval系统.md`

### Code-based 内部计分

```python
# 三维度加权
code_score = (
    0.3 × tool_accuracy +       # 工具调用准确性
    0.5 × policy_compliance +   # 政策合规（权重最高）
    0.2 × output_format         # 输出格式
)

# 政策合规检查
if budget > max_budget:
    policy_compliance = 0.0     # 直接零分
    level = CRITICAL            # 阻断级别
```

### Model-based 内部计分

```python
# 四维度加权（调用 evaluators.py）
model_score = (
    0.35 × correctness +          # 答案正确性
    0.30 × relevance +            # 答案相关性
    0.20 × groundedness +         # 忠实度（无幻觉）
    0.15 × retrieval_relevance    # 检索质量
)

# 每个维度：LLM 评 1-5 分，归一化到 0-1
```

→ final_level = PASS (≥ 0.85)
```

**场景 2：预算超标阻断**
```

model_score = 0.9
→ final_score = 0.6 × 0.5 + 0.4 × 0.9 = 0.66

### 核心知识点总结

#### 1. ✅ State 流转机制（重点掌握）

**State 是 Graph 级别共享的**：
- 创建图时 `StateGraph(AgentState)` 绑定
- 每个节点函数签名：`def node(state) -> dict`
- 返回 dict 自动合并到 State（部分更新）
- 下一个节点自动接收更新后的 State

**State 定义示例**：
```python
class AgentState(TypedDict):
    # 短期记忆
    messages: Annotated[list, add_messages]
    
    # 工作记忆
    intent: str
    entities: dict
    progress: str
    
    # 长期记忆
    user_id: str
    user_profile: dict
    
    # 控制流
    next_agent: str
    results: dict
```

---

#### 2. ✅ Chain vs Agent vs Multi-Agent 的层次关系

**正确理解**：
- Chain：无状态，单向流动
- Agent：有状态，循环执行（Thought → Action → Observation）
- Multi-Agent：LangGraph 编排多个 Agent 协作

**决策表**：
| 场景 | 复杂度 | 用什么 |
|------|--------|--------|
| "北京天气" | SIMPLE | 代码控制或简单 Chain |
| "北京和上海天气" | SIMPLE | 并行 Chain |
| "查天气，下雨推荐" | MEDIUM | ReAct Agent |
| "规划3天出差" | COMPLEX | Multi-Agent |

---

#### 3. ✅ LangChain vs LangGraph 的关系

**互补关系，不是替代关系**：
- LangChain：基础工具包，无状态，单向流动
- LangGraph：编排框架，有状态，循环/分支/条件路由
- 类比：LangChain = React，LangGraph = Next.js

---

#### 4. ✅ Message vs State 的职责分工（重要理解）

**核心理解**：Message 是 State 的一部分

```python
class AgentState(TypedDict):
    messages: Annotated[list, add_messages]  # ← Message 在 State 里
    next_agent: str                          # ← 纯 State 字段
    results: dict                            # ← 纯 State 字段
```

**为什么专门用 Message 对象？**
1. 标准化协议（有角色、时间戳、来源）
2. 对话历史天然表示
3. 生态兼容

**职责分离**：
- Message：负责对话内容
- State 其他字段：负责控制流和中间数据

---

#### 5. ✅ 其他核心知识点

- **Human-in-the-Loop**：`interrupt_before/after` + `checkpointer`
- **多用户区分**：thread_id + checkpointer
- **Agent 交互协议**：HumanMessage/AIMessage/SystemMessage/ToolMessage
- **AgentState 七字段**：messages, query, context, next_agent, results, final_answer, iteration_count
- **条件边**：根据 State 动态路由
- **版本号**：langchain 0.3.x, langgraph 0.2.x
- **模型参数**：temperature（0.0-0.9）、max_tokens、timeout、max_retries

### 🔥 重点追问及深度理解

#### 追问 1: 为什么不通过 state 来交互而是用 message？

**核心理解**：Message 本身就存储在 State 中（`messages` 字段）

**为什么专门用 Message 对象？**
1. 标准化协议：统一格式，有元数据
2. 对话历史：天然表示对话流程
3. 生态兼容：LangChain 所有工具都基于 Message

**职责分离**：Message 负责对话，State 其他字段负责控制流

#### 追问 2: 子图的机制为什么不用 message 代替？

**核心理解**：子图和 Message 是两个维度
- Message：数据传递格式（对话协议）
- 子图：代码组织方式（模块化架构）

**子图的价值**：模块化、复用、隔离、可组合
