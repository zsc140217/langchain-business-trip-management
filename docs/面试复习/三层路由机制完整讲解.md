## 【60秒电梯版】

我们项目是**企业差旅管理系统**，用了**三层路由架构**处理员工查询，核心目标是**节省70%成本、3倍性能提升、保证80%准确率**。

**第1层：固定命令快路径**  
10个高频命令精确匹配，60%请求80毫秒搞定。比如"查询北京天气"直接调工具，不走LLM。

**第2层：LLM意图识别**  
固定命令没命中的，用LLM判断业务域——报销域、政策域、闲聊域。比如"我去北京3天花了850块"识别为报销域，"北京住宿标准"识别为政策域。

**第3层：通道路由+实体识别**  
政策域内部LLM一次性完成三件事：
1. 提取查询实体（城市、否定词、疑问词等）作为判断依据
2. 基于实体判断通道（simple/complex/planning）
3. 基于实体决定检索策略（是否改写、改写方式、RRF参数）

**检索优化（通道内部）**：
- **查询重写**：后退策略（具体地址→城市级别）、否定词处理、口语转标准化
- **三路召回融合**：BM25 + Dense原始 + Dense改写
- **RRF动态调参**：根据实体特征（否定词k=40、疑问词k=50、标准k=60）

**效果**：月成本从6000降到1800，平均响应从1.8秒降到600毫秒，准确率80%。

## 【完整技术深挖版】

### 1. 整体架构：三层路由的职责划分

```
用户查询
  ↓
【第1层：固定命令快路径】
  职责：拦截高频标准操作
  命中 → 直接调工具（80ms）
  未命中 ↓
  
【第2层：LLM意图识别】
  职责：业务域分流
  ├─ 报销域 → 报销引擎处理
  ├─ 闲聊域 → 简单回复
  └─ 政策域 ↓
  
【第3层：通道路由+实体识别+策略决策】
  职责：LLM一次性判断
  ├─ 提取实体（判断依据）
  ├─ 判断通道（simple/complex/planning）
  └─ 决定检索策略（改写+RRF参数）
  ↓
  ├─ Simple通道：单次检索
  ├─ Complex通道：任务分解
  └─ Planning通道：Skill驱动
  ↓
【检索优化（通道内部实现）】
  ├─ 查询重写：根据策略改写
  ├─ 三路召回：BM25 + Dense×2
  └─ RRF融合：根据参数融合
```

**关键点**：
- 第1层和第2层负责**路由决策**
- 第3层负责**实体识别+通道选择+策略决策**（一次LLM调用）
- 检索优化是**通道内部的执行技术**，不是独立路由层

### 2. 第1层：固定命令快路径（60%，80ms）

#### **为什么用固定命令而不是关键词匹配**

**B端场景核心**：员工经过培训，愿意使用固定格式换取效率。

**早期关键词匹配的问题**：

用关键词（"天气"、"酒店"、"报销"），误拦截率30%：

| 用户输入 | 包含关键词 | 误拦截结果 | 正确处理 |
|---------|-----------|-----------|---------|
| "北京的天气会影响住宿标准吗" | 天气、住宿 | 调天气+酒店工具 | 政策咨询（需要LLM） |
| "比较北京和上海的酒店价格" | 酒店 | 单独查酒店 | 对比分析（需要任务分解） |

**固定命令设计（10个）**：

**查询类（4个）**：
- `查询【城市】天气`
- `查询【城市】酒店`
- `查询【出发城市】到【目的城市】航班`
- `查询【城市】差旅标准`

**操作类（4个）**：
- `提交报销申请`
- `查看我的审批`
- `查看我的报销记录`
- `撤销报销申请【编号】`

**帮助类（2个）**：
- `系统使用帮助`
- `常见问题`

**匹配逻辑**：精确匹配前缀+后缀，提取中间参数。只有**完全符合格式**才走快路径，**零误判**。

**推广效果**：
- 2周后采纳率60%
- 85%员工认为"好记"
- 平均3天记住5个常用命令
- 类似快捷键，学习成本低但使用效率高

### 3. 第2层：LLM意图识别（业务域分流）

#### **职责**

判断查询属于哪个**业务域**，不判断复杂度。

#### **三个业务域**

| 业务域 | 判断条件 | 示例 | 路由目标 |
|--------|---------|------|---------|
| **报销域** | 陈述事实+包含数值+操作意图 | "我去北京3天花了850块" | 报销引擎 |
| **政策域** | 假设情况+咨询标准+对比分析 | "北京住宿标准是多少" | 进入第3层 |
| **闲聊域** | 问候/感谢/系统咨询 | "你好"、"谢谢" | 简单回复 |

#### **Prompt设计要点**

**关键1：明确判断条件**

```
【报销域判断条件】（必须同时满足）
1. 陈述已经发生的事实（"我去了"、"花了"）
2. 包含具体数值（天数、金额）
3. 明确操作意图（报销、提交、查询进度）

【政策域判断条件】
1. 询问假设情况（"如果"、"能不能"）
2. 咨询规则标准（"标准是什么"、"能报多少"）
3. 要求对比分析（"哪个"、"比较"）
```

**关键2：Few-shot正反例对照**

| 用户输入 | 域分类 | 判断依据 |
|---------|--------|---------|
| "我去北京3天花了850块" | 报销域 | 事实陈述+数值+暗示报销 |
| "去北京3天能报多少钱" | 政策域 | 假设情况+咨询标准 |
| "我的报销进度" | 报销域 | 查询操作状态 |
| "报销流程是什么" | 政策域 | 咨询规则 |

**关键3：处理信息不足**

当识别为报销域但缺少参数时，**引导补充**而不是拒绝：

```
输入："我想报销去北京的费用"
识别：报销域（信息不足）

输出：
"您想提交北京出差的报销申请，请告诉我：
1. 出差天数
2. 实际花费金额

或者输入'提交报销申请'进入表单填写"
```

**性能数据**：
- 业务域分类准确率：94%
- 平均耗时：300ms（LLM调用1次）
- 处理量：400次/1000次查询（40%）

### 4. 第3层：通道路由+实体识别+策略决策（政策域）

#### **核心：LLM一次性完成三件事**

**传统方案的问题**：
- 方案1：实体识别（规则）→ 通道路由（LLM）→ 策略判断（规则）→ 执行
  - 问题：规则复杂，难维护
- 方案2：通道路由（LLM）→ 策略判断（LLM）→ 执行
  - 问题：多次LLM调用，慢且贵

**我们的方案**：LLM一次性返回完整决策

```
输入：用户查询
  ↓
LLM分析（一次调用）
  ↓
输出JSON：
{
  "entities": {...},              # 提取的实体（判断依据）
  "channel": "simple/complex/planning",  # 通道选择
  "retrieval_strategy": {
    "need_rewrite": bool,
    "rewrite_strategy": "...",
    "rrf_params": {k, weights}
  },
  "reasoning": "..."             # 判断理由
}
```

#### **Prompt设计（核心）**

```
你是查询路由和检索策略专家。请分析用户查询，一次性返回完整的处理策略。

用户查询：{query}

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
第一步：提取查询实体（判断依据）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

请提取以下实体：
1. 城市实体：如"北京"、"上海"，注意识别俚语（魔都→上海、帝都→北京）
2. 具体地址：如"西单"、"SOHO"、"朝阳区"
3. 品牌实体：如"如家"、"希尔顿"
4. 金额实体：如"500元"、"1000块"
5. 否定词：如"不能"、"禁止"、"不允许"
6. 疑问词：如"可以吗"、"能不能"、"是否"
7. 对比词：如"比较"、"对比"、"哪个"
8. 专业术语：如"差旅补贴标准"、"报销限额"
9. 口语化标记：是否包含俚语、语气词

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
第二步：基于实体判断通道
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

【simple】单一问题，一次检索可回答
  触发条件：单个城市 + 无对比词 + 无"安排/规划"

【complex】多步骤，可分解
  触发条件：包含对比词 OR 多个城市 OR 明确的多步任务

【planning】完整方案
  触发条件：包含"安排"、"规划"关键词

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
第三步：基于实体判断检索策略
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

【是否需要改写】
- 包含专业术语 → 不改写（改写会破坏专业性）
- 查询极短（<5字符） → 不改写（改写会过度发挥）
- 其他情况 → 需要改写

【重写策略】（需要改写时）
- 包含否定词 → negation（保留否定词+扩展同义词）
- 包含具体地址/品牌 → step_back（后退到城市/类型级别）
- 包含疑问词 → question（扩展规则词）
- 包含俚语/口语化 → standard（标准化改写）
- 默认 → standard

【RRF参数】k值和权重[BM25, Dense原始, Dense改写]
- 专业术语：k=70, [1.2, 1.0, 0.6]（提高BM25，降低改写干扰）
- 否定词：k=40, [1.5, 0.8, 0.5]（降低k值提高头部权重，加强BM25精确匹配）
- 疑问词：k=50, [1.0, 1.2, 1.0]（加强语义理解）
- 口语化：k=60, [0.8, 1.0, 1.2]（改写效果明显，提高改写权重）
- 具体地址/品牌：k=60, [1.0, 1.0, 0.8]（后退策略，标准参数）
- 默认：k=60, [1.0, 1.0, 0.8]

返回JSON格式...
```

### 5. 检索优化技术（通道内部实现）

**重要**：查询重写和RRF调参不是独立路由层，而是**通道内部根据第3层决策执行的检索技术**。

#### **5.1 查询重写的三大策略**

**策略1：后退提示词（Step-Back Prompting）**

**核心思想**：用户问得太具体时，先退一步问更宏观的问题。

**为什么需要后退**：政策文档的颗粒度是**城市级别、星级分类**，不会细到**地标、品牌**。

| 场景 | 原始查询 | 后退改写 |
|------|---------|---------|
| 具体地址 | "西单附近500元的酒店" | "北京住宿标准 500元上限" |
| 具体品牌 | "住如家快捷酒店能报销吗" | "经济型连锁酒店住宿标准" |
| 特殊时间 | "春节期间去上海出差" | "上海住宿标准 特殊时期" |

**效果**：召回率从60%提升到85%

**策略2：否定词处理（保留+扩展+调参+Rerank）**

**三步处理**：

```
Step 1：保留否定词
"北京出差不能住五星级酒店吗"
→ "北京出差住宿标准 不能 五星级酒店"

Step 2：扩展同义词
原始：不能
扩展：禁止、不允许、不得、上限、限制、超标

Step 3：RRF参数调整
k=40（降低，提高头部权重）
weights=[1.5, 0.8, 0.5]（BM25权重提高）

Step 4：否定词Rerank
融合后Top-10文档重新打分：
  包含否定词：分数×1.5
  不包含否定词：分数×0.7
```

**效果对比**（50个否定查询）：

| 策略 | Top-1准确率 |
|------|------------|
| 标准RRF | 62% |
| 调整k值+权重 | 74% |
| **+ Rerank** | **88%** |

**策略3：疑问词扩展**

```
原始："高铁票可以报销吗"

Step 1：提取核心动词 → 报销

Step 2：扩展规则词
扩展：报销范围、报销条件、交通费用、凭票报销

Step 3：RRF参数
k=50, weights=[1.0, 1.2, 1.0]（加强语义理解）
```

#### **5.2 三路召回融合**

**架构**：

```
改写后的查询
  ↓
并行三路召回：
  ├─ 路径1：BM25稀疏检索（原始查询）
  ├─ 路径2：Dense向量检索（原始查询）
  └─ 路径3：Dense向量检索（改写查询）
  ↓
RRF融合排序
  ↓
返回Top-K文档
```

**为什么是三路而不是两路？**

| 路径 | 优势 | 劣势 | 准确率 |
|------|------|------|--------|
| BM25 | 精确匹配关键词 | 语义理解弱 | 55% |
| Dense原始 | 语义理解强 | 关键词匹配弱 | 65% |
| Dense改写 | 标准化表达 | 可能丢失原意 | 70% |

**融合效果**：
- 两路融合（BM25 + Dense原始）：75%
- **三路融合**：**80%+**

#### **5.3 RRF动态调参**

**RRF公式**：
```
score(doc) = w1/(k+rank1) + w2/(k+rank2) + w3/(k+rank3)
```

**场景化参数配置**：

| 查询特征 | k值 | BM25 | Dense原始 | Dense改写 | 理由 |
|---------|-----|------|----------|----------|------|
| **标准** | 60 | 1.0 | 1.0 | 0.8 | 默认配置 |
| **否定词** | **40** | **1.5** | 0.8 | 0.5 | 精确匹配否定词，头部权重↑ |
| **疑问词** | **50** | 1.0 | **1.2** | 1.0 | 加强语义理解 |
| **口语化** | 60 | 0.8 | 1.0 | **1.2** | 改写效果明显 |
| **专业术语** | **70** | **1.2** | 1.0 | 0.6 | 减少改写干扰 |

**为什么否定查询k=40？**

k值越小，头部文档权重越大。否定查询需要**高精度**，只让真正匹配"不能"的文档排前面。

**计算示例**（文档排名[1,5,3]，权重[1.5,0.8,0.5]）：

```
标准k=60：得分 = 1.5/61 + 0.8/65 + 0.5/63 = 0.0448
否定k=40：得分 = 1.5/41 + 0.8/45 + 0.5/43 = 0.0660（提高47%）
```

#### **5.4 Simple通道的完整执行流程**

```
【Step 1】根据第3层决策，判断是否改写
if need_rewrite == false:
    直接使用原始查询
else:
    根据rewrite_strategy执行改写

【Step 2】三路召回
- BM25检索（原始查询）
- Dense检索（原始查询）
- Dense检索（改写查询，如果改写了）

【Step 3】RRF融合
使用第3层决策的rrf_params
score = w1/(k+rank1) + w2/(k+rank2) + w3/(k+rank3)

【Step 4】可选Rerank
if rewrite_strategy == "negation":
    对Top-10文档重新打分
    包含否定词：×1.5
    不包含否定词：×0.7

【Step 5】LLM生成答案
基于Top-5文档生成自然语言回答
```

#### **5.5 Complex通道的完整执行流程**

```
【Step 1】任务分解
根据第3层的判断，拆解成多个子任务
示例："对比北京和上海"
  → 子任务1："查询北京标准"
  → 子任务2："查询上海标准"

【Step 2】每个子任务独立执行检索
每个子任务都使用第3层决策的retrieval_strategy：
  - 改写查询
  - 三路召回
  - RRF融合
  - 返回结果

【Step 3】结果合成
LLM综合所有子任务结果，生成对比分析
```

## 【背诵版口诀】

**三层职责**：
- **第1层**：固定命令拦截高频（60%/80ms）
- **第2层**：意图识别分流业务域（报销/政策/闲聊）
- **第3层**：LLM一次性判断（实体+通道+策略）

**第3层的三维判断**：
1. **提取实体**：城市、地址、否定词、疑问词、专业术语、口语化标记
2. **判断通道**：simple（单一）/complex（多步骤）/planning（完整方案）
3. **决定策略**：是否改写、改写方式、RRF参数

**检索优化（通道内部）**：
- **查询重写**：后退（具体→抽象）、否定（保留+扩展）、疑问（核心+规则）、口语（标准化）
- **三路召回**：BM25 + Dense原始 + Dense改写
- **RRF调参**：否定k=40/BM25↑、疑问k=50/Dense原始↑、口语Dense改写↑、专业k=70/不改写

**核心亮点**：
1. **一次LLM调用完成三个判断**（实体+通道+策略）
2. **判断依据明确**（基于提取的实体）
3. **可解释性强**（reasoning说明判断理由）
4. **与记忆系统结合**（实体存入工作记忆）

**一句话总结**：三层路由通过**固定命令、意图识别、LLM一次性判断（实体+通道+策略）**实现分层过滤，通道内部根据决策执行**查询重写、三路召回、RRF动态调参**，在B端场景下实现70%成本节省、3倍性能提升、80%准确率。

## 【难点和追问准备】

### 追问1：为什么允许准确率降2%？

因为快路径误判的代价可控。比如"北京天气"被误拦截，调用天气工具，用户仍能得到正确答案。如果真的拦截错了，第2层LLM会兜底纠正。**用2%的准确率换70%的成本节省**，ROI非常高。

### 追问2：为什么不用纯LLM路由？

纯LLM路由准确率高（96%），但慢（1.8秒）且贵。简单查询像"北京天气"也要调LLM，浪费。我们的方案是**80/20原则分层处理**：80%简单高频问题用固定命令拦截，20%复杂问题用LLM精准处理。

### 追问3：为什么是三层而不是四层？

三层已经覆盖了**简单→中等→复杂**的梯度。再增加一层，收益递减（边际效益<10%），但复杂度大增。遵循"奥卡姆剃刀原则"：**够用就好，不要过度设计**。

### 追问4：固定命令推广困难怎么办？

三个策略：
1. **降级兜底**：自然语言照样能用，只是稍微慢一点
2. **智能提示**：输入"北京天气"提示"建议使用'查询北京天气'，响应更快"
3. **渐进引导**：前3次自动转换并展示，第4次用户会主动用命令

### 追问5：实体识别准确率如何保证？

LLM的实体识别能力已经很强，我们在Prompt中给了明确的实体类型定义和示例。同时提取的实体会存入工作记忆，如果识别错误可以从用户反馈中学习优化。

### 追问6：遇到过什么坑？

**坑1**：早期查询重写过度，专业术语也改写，导致准确率下降。解决：增加"专业术语不改写"的判断。

**坑2**：否定查询容易被"肯定文档"干扰。解决：增加否定词Rerank步骤，包含否定词的文档分数×1.5。

**坑3**：RRF参数凭感觉设置，效果不稳定。解决：做了网格搜索实验，用100个标注查询测试20种参数组合，选择准确率最高的配置。
