## 1. 系统架构话术

### Q1.1: 请介绍一下整体系统架构

**简洁回答（1分钟版）**:

"这是一个企业级AI差旅管理系统，采用前后端分离架构。后端基于FastAPI构建统一API网关，核心是OrchestratorAgent智能路由器，根据查询复杂度分发到QA域或审批域。前端使用React 19 + TypeScript，实现了旅行文档美学的UI设计。整个系统支持对话式交互，用户通过自然语言完成政策查询、报销申请等操作。"

**技术细节（3分钟版）**:

"我们的架构分为四层：

**第一层：统一API网关**（端口8001）
- 基于FastAPI实现RESTful API
- JWT Token认证，支持用户身份识别
- CORS跨域配置，支持前端独立部署
- 全局异常处理和日志记录

**第二层：智能路由层**（OrchestratorAgent）
- 意图识别：识别用户是查询政策还是申请报销
- 三层路由架构：
  - 第零层：关键词匹配（0次LLM调用）
  - 第一层：Self-RAG分类器
  - 第二层：复杂度评估器
- 路由决策延迟<200ms，准确率95%+

**第三层：业务执行层**
- QA域：处理政策查询，采用Fusion Retrieval（向量+BM25融合）
- 审批域：处理报销申请，基于LangGraph状态机编排
- 工具层：集成航班、酒店、天气等外部API

**第四层：数据存储层**
- PostgreSQL：用户、会话、消息、审批数据
- Redis：缓存、会话状态、实时预算扣减
- Milvus：向量数据库，存储政策文档embedding

**横向支撑：三层记忆系统**
- 对话记忆：会话内上下文（Redis）
- 用户画像：偏好和历史（PostgreSQL）
- 工作记忆：任务状态（内存 + Redis）"

**数据支撑**:
- 端口配置：前端5173，后端8001
- 响应时间：P99 < 3s
- 并发支持：100+ QPS（单机）
- 数据库表：users, conversations, messages, approvals, policies

**面试官可能追问**:
- "为什么选择FastAPI而不是Django？"
  - 回答：FastAPI异步支持更好，适合IO密集型AI应用；自动生成API文档；类型提示和数据验证；性能是Django的2-3倍
- "如何保证高可用？"
  - 回答：目前是单机部署，生产环境计划使用Kubernetes部署多副本；数据库读写分离；Redis集群模式；LLM调用有降级策略

### Q1.2: 为什么采用事件驱动架构？与RPC调用相比有什么优势？

**简洁回答**:

"我们在模块间通信时选择事件驱动而不是直接RPC调用，主要有三个原因：解耦、可追溯、易扩展。通过事件总线（EventBus），各模块只依赖事件接口，不依赖具体实现，降低了耦合度；每个事件都有TraceID，方便问题排查；新增消费者无需修改发布者代码。"

**技术细节**:

"我们基于Redis Stream实现了轻量级事件总线：

**发布端**:
```python
EventBus.publish("approval.submitted", {
    "trace_id": trace_id,
    "user_id": user_id,
    "approval_data": {...}
})
```

**消费端**:
```python
@EventBus.subscribe("approval.submitted")
def handle_approval(event_data):
    # 业务逻辑处理
    pass
```

**核心优势**:
1. **解耦**：审批提交后发布事件，飞书通知、邮件提醒、数据统计等消费者独立订阅，互不影响
2. **异步**：发布立即返回，不阻塞主流程，提升用户体验
3. **可靠性**：Redis Stream的ACK机制保证消息不丢失，消费者崩溃后可以重新消费
4. **可追溯**：每个事件携带TraceID，在LangSmith中可以查看完整链路
5. **易扩展
