DashScope API vs 本地微调模型

评估时间：2026年6月14日 & 2026年6月22日

📋 核心发现

⚠️ 关键问题：测试集不一致导致结果无法直接对比

两次评估使用了完全不同的测试集，导致性能指标产生了巨大差异。新评估使用的简化测试集（17查询 + 10文档）比旧评估的完整测试集（20查询 + 29文档）难度显著降低。

✅ 正确结论：本地微调模型在真实场景下劣于通用API

基于完整测试集的评估显示，DashScope API的Recall@5为83.33%，而微调模型仅为76.47%。通用大模型在复杂查询和干扰文档环境下表现更优。

📊 两次评估详细对比

评估一：完整测试集（6月14日）
  • 测试集：enhanced_test_set.json
  • 查询数量：20个（5 easy + 7 medium + 5 hard + 3 distractor）
  • 文档数量：29个（包含大量语义相似的干扰文档）
  • 特点：真实业务场景，高难度
结果：
DashScope API 83.33%
微调模型 76.47%
评估二：简化测试集（6月22日）
  • 测试集：test_generator.py（硬编码）
  • 查询数量：17个（4 easy + 7 medium + 5 hard + 1 distractor）
  • 文档数量：10个（干扰项极少）
  • 特点：理想化场景，低难度
结果：
DashScope API 88.24%
微调模型 94.12%
🔍 差异分析
  • 文档数量减少70%：29个 → 10个，检索难度大幅降低
  • 干扰项减少67%：3个distractor → 1个distractor
  • 查询更直接：新测试集的查询关键词匹配度更高
  • 结果反转原因：简化场景掩盖了微调模型在复杂环境下的泛化能力不足

💡 核心收获与经验教训

1️⃣ 测试集设计至关重要

错误做法：使用硬编码的简化测试集（test_generator.py），文档少、干扰项少，无法反映真实场景。

正确做法：使用包含充足干扰项的完整测试集（enhanced_test_set.json），模拟真实检索环境。

教训：永远不要用"理想化"的测试集评估模型，否则会得出错误结论。

2️⃣ 微调≠性能提升

发现：基于200组样本微调的BGE-large-zh模型，在真实场景下Recall@5反而比通用API低6.86%。

原因：

  • 训练数据不足（200组）导致过拟合
  • 训练样本未覆盖足够的语义变化
  • 通用大模型（千问）的预训练规模和数据多样性远超本地微调

建议：除非有10,000+高质量标注数据和充足的领域特异性需求，否则优先使用通用API。

3️⃣ 评估指标的选择

Recall@5 vs Accuracy@1：

  • Recall@5：衡量检索覆盖能力，真实RAG场景更关注这个指标
  • Accuracy@1：微调模型更高（41.18% vs 33.33%），但Recall@5更低，说明"猜对第一个但漏掉其他相关文档"

结论：RAG系统应优先关注Recall@K，而非Accuracy@1。
